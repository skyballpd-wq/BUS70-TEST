# BUS70-TEST
소신여객 70번·5번 통합 운행 관리 테스트 버전

## v62 기사 운행 화면과 자동기록

- 현재 탕 카드에 예정·실제·시간 차이, GPS 속도, 정류장 연결도, 앞뒤 차량의 예정 간격과 GPS 추정 간격을 구분해 표시합니다. 정류장 N개를 N등분한 원형 진행률을 사용하며 오래된 GPS 값은 현재 값으로 표시하지 않습니다.
- 출발, 회차 도착·재출발, 등록된 중간 기준점, 도착/영업종료, 차고지 복귀를 좌표·방향·연속 GPS 수신으로 판정합니다. 중간 시작은 해당 탕의 시작지로 처리합니다. 예정시각만으로 실제 운행기록을 생성하지 않습니다.
- 좌표, 위치 권한, 정상 통신이 필요합니다. 웹은 화면 활성 상태에서, Android v62는 기존 전면 위치 서비스를 사용해 자동기록합니다. 이 릴리스의 합성 GPS 테스트는 실제 노선 주행 검증을 대체하지 않습니다.
- 경로 그림은 정류장 좌표 연결도입니다. 도로별 회전 안내·교차로 신호 카운트는 아직 연동하지 않았습니다. 진행방향에 맞는 검증된 신호 자료가 없으면 미연동으로 표시합니다.
- 날씨는 기상청 초단기실황 API의 5km 격자 관측값입니다. 기존 공공데이터 키에 해당 API 활용승인이 있어야 하며, 인증 실패·누락·오래된 관측값을 날씨 값으로 대체하지 않습니다.
- 수기 판독이 어려운 수정은 기존 DB 값을 유지하고 소장이 나중에 수정합니다. 예정시간과 실제 기록은 분리하고 기존 운행일지 열·이력을 보존하며 새 단계 열만 추가합니다.

## 통합 운영 정규화

- 70번 양성기사와 5번 정규직·예비기사 운영을 함께 수용하는 데이터·권한·실시간 처리 기준은 [`docs/platform-normalization.md`](docs/platform-normalization.md)를 따릅니다.
- 기존 기록은 삭제하거나 덮어쓰지 않고 사람·고용·사번·노선 배치 이력으로 단계적으로 전환합니다.

## 안전 배포

- 배포 폴더에서 `./deploy-bus70.ps1`을 실행하면 먼저 GitHub의 최신 배포 스크립트를 확인합니다.
- 스크립트가 바뀌었으면 기존 파일을 `deploy-bus70.ps1.previous`로 보관하고 최신판으로 한 번만 자동 재실행합니다.
- 공개 저장소에는 계산 로직과 합성 테스트 데이터만 둡니다. 실명·사번·차량 배치·실제 운행시간은 `RoutePrivateData.js`에 분리하며 이 파일은 Git에 올라가지 않습니다.
- 분리 파일이 아직 없으면 현재 배포 폴더, 최근 외부 백업, 로그인된 Apps Script 프로젝트 순서로 기존 자료를 자동 복구합니다. 복구한 뒤 실제 자료만 `RoutePrivateData.js`로 추출하고 공개 모듈을 교체합니다. 기존 서버에 한 노선의 별도 기준 모듈만 있으면 그 노선부터 이관하고, 다른 노선의 기존 스프레드시트 배차 기록은 그대로 보존합니다. 세 위치 어디에도 노선자료가 없을 때만 데이터 손실을 막기 위해 배포를 중단합니다.
- 업로드 직전 공개 모듈과 비공개 데이터 파일의 기능 표식 및 JavaScript 문법을 검사합니다.
- 정상 출력에는 `PrivateRouteStore.js`, `PublicTransitApi.js`, `RoutePrivateData.js`, `Route5Schedule.js`, `Route70Schedule.js`가 모두 표시되어야 합니다.

## 배차판 사진 확인 등록

- `apps-script/BoardEntry.gs`를 Apps Script 프로젝트에 추가합니다.
- `Code.gs`의 `doPost`가 `validateDispatchBoard`, `registerDispatchBoard`를 `bus70AuthAction_`으로 전달해야 합니다.
- 사진은 휴대폰에서 참고용으로만 표시되며 서버나 외부 AI 서비스로 전송되지 않습니다.
- 사용자가 입력한 날짜·순차·차량번호 뒤 3자리만 차량DB·시간표·기존 배차와 대조합니다.
- 검증 결과는 10분 동안만 임시 보관되며 사용자가 최종 확인해야 `배차DB`에 등록됩니다.

## 소장용 날짜·노선별 배차 현황

- `apps-script/ManagerDispatch.gs`는 소장 권한 사용자가 전체 노선 현황을 확인하거나 70번·5번을 선택해, 해당 날짜 시간표에 실제 존재하는 순차별 기사와 차량을 저장합니다.
- `배차DB`에는 `노선` 열을 무중단 추가하며, 기존 노선 값이 없는 행은 70번 과거 자료로 해석합니다. 새 배차 ID에는 노선을 포함해 같은 날짜·순차라도 노선끼리 충돌하지 않게 합니다.
- 기사 모바일은 현재 소속만 고정 표시하지 않고 `driverId + 적용일 이력 + 당일 확정 배차`로 노선을 결정합니다. 과거는 당시 운행기록, 현재·예정은 확정 스케줄을 우선 표시합니다.
- 운행일지 새 기록에는 당시 기사명·사원번호·노선·배차 ID를 스냅샷으로 함께 보존합니다. 사번이나 노선이 바뀌어도 과거 기록의 당시 문맥은 변하지 않습니다.
- 노선 기준자료는 정류장 목록과 상황판·시간표 가용 상태를 `routeProfile`로 제공합니다. 소장은 전체 노선 요약 또는 한 노선 상세를 선택하고, 기사는 당일 배정 노선의 스케줄과 정류장을 확인합니다.
- `Code.gs`의 `doPost`가 `managerDispatchBootstrap`, `saveManagerDispatchDay`도 `bus70AuthAction_`으로 전달해야 합니다.
- 소장 권한은 `계정DB`의 `권한=소장/관리자` 또는 스크립트 속성 `BUS70_MANAGER_DRIVER_IDS`로 제한합니다.
- 초기 운영계정과 비밀번호는 공개 소스가 아니라 로컬 비공개 설정 또는 스크립트 속성 `BUS70_BOOTSTRAP_ACCOUNTS_JSON`에서 관리하며, 마스터 전용 계정관리 요청으로 소장 계정을 추가·변경·중지할 수 있습니다.
- 저장 전 기사·차량 중복과 시간표 연결을 검증하고 변경 내역을 `변경이력DB`에 기록합니다.
- 상황판·시간표 OCR은 저장값과 대조하는 보조 수단이며 OCR 결과만으로 배차를 자동 확정하지 않습니다.
- 생성된 PNG는 Web Share 기능으로 카카오톡 채팅방 선택 화면에 전달합니다. 카카오톡 정책상 채팅방 선택과 최종 전송은 사용자가 수행합니다.

## 노선 기준자료의 비공개 분리

- `apps-script/PrivateRouteStore.gs`가 날짜별 노선자료의 유일한 진입점입니다. 배포 환경에서는 우선 노선별 시트에서 읽고, 아직 이관되지 않은 날짜는 로컬 전용 `RoutePrivateData.js` 또는 스크립트 속성 `BUS70_PRIVATE_ROUTE_DATA_JSON`을 승인 기준자료로 사용합니다.
- 정류장과 기준 배차시간표는 `노선_5_정류장DB`·`노선_5_배차스케줄DB`, `노선_70_정류장DB`·`노선_70_배차스케줄DB`처럼 노선별로 물리 분리합니다. 다른 노선 추가 시에도 같은 명명 규칙을 사용합니다.
- 소장 또는 마스터가 노선을 처음 열면 해당 노선 시트를 준비하고, 승인 기준자료에서 아직 없는 정류장·시간표 행만 비파괴 이관합니다. 기존 행은 자동으로 수정하거나 삭제하지 않습니다.
- 정류장 변경은 적용 시작일·종료일·상태로, 시간표 변경은 운행일·시간표 버전·순차·탕으로 구분합니다. 기사·차량의 당일 확정값은 노선 간 대체 운행을 지원하기 위해 공통 `배차DB`에 노선 키와 함께 유지합니다.
- `apps-script/Route5Schedule.gs`와 `apps-script/Route70Schedule.gs`에는 시간 계산·배차간격·기사 연결 로직만 있으며, 실제 날짜별 명단과 시간표는 포함하지 않습니다.
- 선택 노선의 배차스케줄DB와 승인 기준자료가 모두 없으면 임의의 배차를 만들지 않고 `ROUTE_REFERENCE_NOT_CONFIGURED` 오류를 반환합니다.
- 소장 화면은 요청한 노선·날짜와 서버 응답의 노선·날짜가 다르거나 응답에 노선 값이 없으면 렌더링을 중단합니다. 따라서 5번 선택 화면에 70번 과거 자료가 대신 표시되지 않습니다.
- `노선별 배차시간표 전체 편집`에서 한 날짜의 모든 순차·탕별 발차/회차/도착 시간을 펼쳐 보고 여러 셀을 한 번에 저장합니다. 저장할 때 변경 전 시간이 현재 DB와 같은지 다시 검사하여 오래 열린 화면의 덮어쓰기를 차단합니다.
- 일괄 수정은 기존 시간표 행을 삭제하지 않고 해당 탕의 새 개정 행과 `배차간격조정DB` 이력을 함께 추가합니다. 변경 사유·처리자·개정번호·확정시간을 보존하고 그날 기사 확인을 `재확인필요`로 전환합니다.
- 공개 테스트는 미래의 가상 날짜, 가상 기사, 가상 차량으로만 같은 구조와 예외 규칙을 검증합니다.

## 공공데이터 노선별 정류장 동기화

- 실제 연결 전 `apps-script/PublicApiCheck.gs`를 현재 Apps Script 프로젝트에 추가하고 `BUS70_checkPublicApi`를 실행합니다. 이 독립 점검은 저장된 키로 경기도 버스노선 v2의 노선목록 → 노선정보 → 경유정류소를 조회합니다. 정확한 노선번호·부천 지역·소신여객 운수사를 모두 대조한 후보가 하나일 때만 정류장 개수와 좌표 개수를 출력하며, 속성·노선 설정·정류장DB는 변경하지 않습니다. 경기도 노선ID는 `GYEONGGI_BUS_ROUTE_V2` 공급자 설정으로만 저장하며 국토교통부 `RTE_ID`와 혼용하지 않습니다. 서비스 미승인 오류는 공공데이터포털의 `경기도_버스노선 조회` 활용신청 상태를 확인합니다.
- `apps-script/PublicTransitApi.gs`는 경기도 버스노선 v2와 기존 국토교통부 노선별 경유정류장 API를 공급자별로 분리하여 서버에서만 호출합니다. 인증키는 공개 소스·브라우저 응답·스프레드시트·로그에 기록하지 않습니다.
- Apps Script의 스크립트 속성 `BUS70_DATA_GO_KR_SERVICE_KEY`에 인증키를 보관합니다. 화면 캡처나 채팅에 노출된 키는 폐기·재발급한 뒤 새 키만 등록합니다.
- 속성이 50개를 넘어 프로젝트 설정 화면이 읽기 전용이면, 연결된 스프레드시트를 열어 둔 상태에서 Apps Script 편집기의 `BUS70_setupPublicDataKey`를 실행합니다. 스프레드시트 탭에 나타난 입력창에 인증키를 붙여넣으면 해당 속성 하나만 저장합니다. 취소·빈 입력은 기존 키를 보존하며 로그인 세션과 다른 속성은 삭제하지 않습니다. 키 저장 완료는 외부 API 연결 성공과 구분합니다.
- 5번·70번 최초 연동: 임시 `PublicApiSetup.gs`를 `PublicTransitApi.gs`로 이름 변경하고 이 저장소의 내용으로 교체한 뒤 `PrivateRouteStore.gs`도 함께 갱신합니다. 기존 웹앱의 배포 관리에서 새 버전을 반영하여 새 자료세트 읽기 기능을 먼저 활성화합니다. 그 다음 편집기에서 `BUS70_importGyeonggiRouteStops`를 실행하면 두 노선을 조회해 부천·정확한 노선번호·소신여객을 검증하고 연결 설정을 저장한 다음 노선별 정류장DB에 새 자료세트를 추가합니다. 키 재입력이나 별도 경기도 노선ID 수기 입력은 필요하지 않습니다. 앱의 정류장 표시·운행 진행률은 저장 후 별도로 확인해야 합니다.
- 경기도 가져오기는 정류장 순서·ID·이름·좌표, 하나의 회차점과 노선 정보의 일치를 검증합니다. 전체 왕복 순서를 유지하고 동일 이름·동일 정류장ID가 다시 등장해도 순서별로 보존합니다. 회차점은 `회차점` 열에 저장하고 기사 화면은 이 지점을 경계로 실제 복귀 쪽 정류장을 사용합니다. 현재 API 자료를 과거 운행일에 소급 적용하지 않으며 `자료기준일`(조회일)과 `적용시작`(선택일)을 구분합니다.
- 같은 내용을 재실행하면 저장행수는 0이며 이전 이력, 로그인 세션과 다른 노선 설정은 보존됩니다. 두 노선 모두 사전 검증한 뒤 쓰기를 시작하고, 쓰기 도중 한 노선이 실패하면 이미 저장한 노선의 결과를 로그에 남깁니다. 재실행으로 이어서 적용할 수 있습니다.
- 비밀이 아닌 노선별 외부 식별자는 `BUS70_PUBLIC_ROUTE_API_CONFIG_JSON`에 둡니다. 아래 예시는 기존 국토교통부 공급자를 수동 설정할 때에만 사용합니다. 경기도 5번·70번은 위 함수가 공급자와 노선ID를 자동 설정합니다.

```json
{
  "routes": {
    "5": {"routeId":"PUBLIC_ROUTE_ID_5","routeNo":"5","ctpvCode":"41","sggCode":"PUBLIC_SGG_CODE","coordinateEnabled":true},
    "70": {"routeId":"PUBLIC_ROUTE_ID_70","routeNo":"70","ctpvCode":"41","sggCode":"PUBLIC_SGG_CODE","coordinateEnabled":true}
  }
}
```

- 소장 화면의 `노선별 정류장 공공데이터 동기화`에서 연결 설정 확인 → 미리보기 → 적용 순서로 실행합니다. 적용 시 노선번호가 다르면 중단하고, 미리보기 이후 응답이나 기존 좌표가 바뀌어도 저장을 중단합니다.
- 한 번의 적용 결과는 `자료세트ID`가 같은 완전한 정류장 원장으로 추가합니다. 이전 자료는 삭제하지 않으며, 해당 적용일에는 가장 최신의 완전한 자료세트만 기사 화면에 전달합니다.
- 경기도 노선 API는 정류장 순서·ID·이름·좌표·회차점을 함께 제공하므로 정류장 이름별 좌표 보완 조회를 하지 않습니다. 기존 국토교통부 노선별 경유정류장 API는 정류장 순서·ID·이름을 제공하고 좌표는 제공하지 않습니다. 서버는 경기도 정류소 조회의 공식 `getBusStationListv2`를 별도로 호출해 `stationId`를 먼저 대조하고, 일치할 때 `x·y`를 경도·위도로 저장합니다. 기본 좌표 URL은 `https://apis.data.go.kr/6410000/busstationservice/v2/getBusStationListv2`이며 쿼리가 포함된 주소나 공공데이터포털 외 주소는 거부합니다.
- 같은 정류장명이라도 상행·하행 정류장ID와 좌표가 다르면 정상적인 별도 정류장으로 보존합니다. 정류장명은 고유키로 사용하지 않으며 `외부정류장ID + 노선 내 순서 + 방향`으로 운행상의 정류장 발생을 구분합니다.
- 외부 정류장ID가 맞지 않을 때는 기존의 동일 발생 정류장·동일 외부ID 좌표를 우선 보존합니다. 그 다음 정류장번호 또는 정확히 같은 이름의 좌표가 하나뿐일 때만 보조 연결합니다. ID·번호 없이 이름만 같은 상·하행 후보가 둘 이상이면 임의 선택하지 않고 `좌표보완필요`로 남깁니다. 이름 연결은 `이름일치검토`로 표시하고 좌표 출처는 별도 `좌표제공처` 열에 기록합니다.
- 좌표 API 권한·통신 문제가 생겨도 노선 정류장 순서 전체를 폐기하지 않습니다. 미리보기에 경고와 미해결 개수를 표시하고 기존 검증 좌표를 보존하며, 소장 또는 마스터가 검토한 완전한 자료세트만 적용합니다. 동일 검색어의 공개 좌표 응답은 서버 캐시에 6시간 보관해 일일 호출량과 대기시간을 줄입니다.

## 운행 규칙 보존 원칙

- 노선마다 첫 운행 번호, 중간 출발, 단축 종료, 왕복 종료, 차고지 회귀 같은 운행 형태를 별도 필드로 기록하며 존재하지 않는 탕을 임의로 만들지 않습니다.
- 순차의 첫 운행은 `1탕`으로 고정하지 않고 해당 날짜·시간표 버전·순차에 실제 등록된 탕 번호의 최솟값으로 결정합니다. 화면, 알람, 캘린더, 위치기록, 시간변경은 같은 실제 탕 목록만 사용합니다.
- 인쇄 시간표는 원본으로 보존합니다. 수기 조정은 노선·운행일·순차·탕·발차/회차/도착·변경 전후 시간·사유·단톡방 공지 근거를 별도 이력으로 저장하며, 소장 또는 마스터가 확정한 행만 기사 스케줄과 알람에 적용합니다.
- 상황판에서 확인된 기사·차량 배치와 시간표 행은 분리하여, 사진에 없던 배치를 임의로 만들지 않습니다.
- 기사 이름이 당일 상황판과 일치하면 기존 배차DB에 아직 행이 없어도 모바일 스케줄·알람용 운행정보를 반환합니다.
- 각 탕의 앞차·뒷차 간격은 같은 탕에서 실제 출발시간이 있는 인접 순차를 기준으로 계산합니다.
- 테스트 중에는 로그인한 본인만 검증된 내부 기사 ID와 연결하고, 다른 기사는 사번 없는 날짜·노선·순차 기반 가상 ID로 연결합니다. 운영 전환 시 검증된 실제 계정으로 매핑하되 기존 배차·운행 기록은 보존합니다.
- 배차DB에 확정 행이 있으면 확정 행을 우선하며, 사진 기준자료는 확정 행이 없을 때 기사 모바일 스케줄·알람 검증용으로만 사용합니다.

## 기사 탕별 진행·운행기록

- 기사 화면은 현재 탕과 전체 탕 목록에 원형 진행률과 이동 화살표를 표시합니다. 정류장 좌표가 있으면 GPS 노선 진행률을 쓰고, 좌표가 없을 때는 발차·회차·도착 기록 단계로 진행률을 표시합니다.
- 각 탕은 `순차 첫 운행 시작지`, `회차·복귀 구간 시작지`, `탕 운행 종료지`, `막탕 상행 영업종료지`, `막탕 회송 복귀지`처럼 지점 역할을 함께 표시합니다. 다음 탕 시작지와 같은 지점도 별도로 구분합니다.
- 운행일지에는 발차·회차·도착의 계획시간과 실제시간, 자동·수동 기록방식, 계획 대비 분 단위 편차를 저장·조회·인쇄합니다.
- 새 운행기록에는 당시 발차지·회차지·도착지와 역할을 스냅샷으로 보존하므로 이후 노선이나 시간표가 바뀌어도 당시 기록의 의미가 유지됩니다.


## v60 고강차고지 업무 화면

- 소장 공통 노선·날짜 선택 아래 업무 홈을 제공하고 배차, 근태·대체, 기사, 차량·정비, 연락망, 계정 화면으로 전환합니다.
- 기사 선택은 선택 노선 안에서 근무조·이름순으로 정렬합니다. 다른 노선 지원은 별도 대체 범위와 사유가 필요합니다. 서버는 노선이 다른 자동 일괄 배정을 거절하고 동일 날짜 다른 노선의 중복 배정도 검사합니다.
- 기사 화면 기본값은 탕별 카드입니다. 계획·실제 시각, GPS 위치·속도, 앞뒤 차량 간격과 자료 시점을 함께 표시합니다. GPS가 오래되거나 부정확하면 정류장 기반 진행률을 표시하지 않습니다. GPS 진행률은 정류장 좌표에서 추정한 통과 개수이며 정밀 도로 지도나 차선 안내는 아닙니다.
- 긴급연락망의 사무실·주간소장·야간소장·안전관리자·정비소 번호는 소장 화면에서 등록합니다. 번호는 공개 코드에 넣지 않으며 인증된 서버 요청으로만 조회·수정합니다.
- 신호 카운트는 연결 대기 상태입니다. 공식 API는 방향별 신호 상태와 잔여시간을 제공하지만, 5·70번 경유 교차로의 실제 제공 범위·방향 매칭·신선도 검증은 아직 완료되지 않았습니다. 실제 신호와 시차가 날 수 있으므로 임의 카운트는 표시하지 않습니다. 공식 명세: https://www.data.go.kr/data/15157604/openapi.do
- 배포 순서: 기존 Apps Script 프로젝트의 공개 모듈 전체를 함께 갱신하고 기존 배포 ID에 새 버전을 적용한 다음 웹 화면을 배포합니다. `RoutePrivateData`와 인증키·계정·노선별 정류장DB는 그대로 보존합니다. 정류장 수집 성공만으로 날짜별 배차시간표가 생성되지는 않습니다.


### v60.3 입력·조회 및 DB 연결 보완
- 한글 입력기가 동작하지 않는 환경을 위해 사용자가 요청할 때만 작동하는 두벌식 변환 도우미를 제공합니다. 한글 조합 중 Enter로 로그인을 제출하지 않으며 로그인 이름을 NFC로 정규화합니다.
- 근무조는 서버에서 확인된 날짜·조를 기준으로 날짜 차이만큼 계산하고, 확인된 기준이 없으면 확인 대기로 표시합니다.
- 이미 모든 순차가 확정된 날은 과거 배차 예측 스캔을 생략합니다. 기존 연도별 공휴일 조회 캐시와 함께 적용합니다.
- 노선별 시간표에 시간기준지·시간기준시각·시간기준설명을 추가해 막차 기준 정류장과 회차를 분리합니다. 기존 열과 API 필드는 유지합니다.
- 프런트엔드의 입력 도우미·날짜 표시 보완은 기존 서버 API와 호환되므로 독립 배포 가능합니다. 조회 성능 및 기준 정류장 처리는 ManagerDispatch.gs, PrivateRouteStore.gs, Route5Schedule.gs를 함께 저장하고 기존 웹앱 배포 ID에 새 버전을 적용해야 활성화됩니다.
- 실제 기사·차량·휴무·날짜별 시간표는 공개 저장소에 넣지 않습니다. 원본 근거와 적용 날짜를 보존하면서 연결된 비공개 DB에서 검증합니다.

- `node tests/work-return.test.js`에서 실제 저장 함수와 연결해 복귀 저장, 이전 날짜의 상태, 배차 보존, 일반 대체 입력 검사를 검증합니다.

### v60.5 기사 일정 조회 세션 복구
- 운행정보 조회는 현재 기사 상태를 검증하는 `session` 요청의 날짜별 일정을 사용합니다. 중복 통합 또는 종료된 기사 항목의 오래된 로그인이 남으면 로그인 화면에서 최신 계정으로 다시 연결합니다.
- 재직 기사의 실제 미배차 응답은 그대로 표시하며, 날짜·로그인 변경 후 도착한 이전 응답은 무시합니다. 클릭 이벤트가 자동 갱신으로 오인되어 조회 중 표시를 생략하던 부분도 수정했습니다.
- 기존 서버의 `session` 기능을 사용하므로 Apps Script 재배포는 필요하지 않습니다. `node tests/schedule-session-recovery.test.js`로 종료된 세션, 정상 일정, 실제 미배차, 구형 응답 및 늦은 응답을 검증합니다.

## v61 기사 자동 기록과 월별 시간표

- 기사 첫 화면은 현재 탕 카드 한 장에 계획·실제·편차, 다음 정류장, 속도, 앞뒤차 간격을 표시합니다. 기사 신상·날짜 선택·수동 기록·상세 설정은 접어 두며 일정은 60초 간격으로 다시 확인합니다. 계정·날짜·배차 변경 뒤 도착한 이전 저장 응답은 새 화면에 적용하지 않습니다.
- GPS는 기사가 한 번 켜고 위치 권한을 허용한 기기에서만 자동 재개합니다. 동명 정류장은 기점/회차점/복귀 방향의 발생 순서로 구분합니다. 확인되지 않은 별칭은 좌표를 추측하지 않습니다. 시각만으로 운행 완료 기록을 생성하지 않습니다.
- 발차는 기점 안의 연속 위치 확인 후 이탈, 회차·도착은 올바른 순서의 연속 진입으로 판정합니다. 20초 이상 오래된 위치, 60m보다 부정확한 위치, 같은 위치시각의 반복 수신은 기록 근거로 사용하지 않습니다. 출발 기준점에서 이미 벗어난 뒤 앱을 켜면 누락된 발차를 자동으로 만들어내지 않습니다.
- `driver-automation.js`의 모의 궤적 검증은 실제 도로·휴대폰 검증과 다릅니다. 일반 브라우저의 화면 꺼짐 추적은 보장하지 않으며 Android 위치 전경 서비스의 기기 시험이 필요합니다. 통신 장애로 저장하지 못한 이벤트를 저장 완료로 표시하지 않습니다.
- 소장 근태 메뉴의 `정규전환`은 기사·적용일·새 정규 사번을 받아 기존 이력 처리 경로로 저장합니다. 노선과 근무조를 미리 채우고 필요한 경우만 바꿉니다. 기사 ID, 기존 배차·운행 기록, 예비 배치 정보와 차량 배정은 보존합니다.
- 날짜별 시간표는 `노선_<노선>_배차스케줄DB_YYYY_MM`에 저장합니다. 해당 월 시트가 있으면 그 월만 읽고, 이관 전 월은 기존 시트에서 읽습니다. 새 월은 필요한 기존 행만 비파괴 복사한 뒤 생성합니다. 새 개정과 사진 기준자료의 시간표 쓰기도 같은 월로 보냅니다. 월별 시트 행이 부족하면 자동 확장합니다.
- 과거 패턴 예측은 요청 월과 앞선 두 달까지만 읽습니다. 그 범위에 근거가 없으면 예측을 제공하지 않습니다. 정류장은 변경 이력이 있는 별도 노선 원장에 유지하며 임의로 월별 복제하지 않습니다. `배차DB`와 `운행일지`는 이번 시간표 분할 대상이 아닙니다.
- **서버 적용:** `PrivateRouteStore.gs`, `ManagerDispatch.gs`, `AuthStep9.gs`를 함께 갱신한 뒤 기존 웹앱 배포에 새 버전을 적용해야 월별 조회·쓰기와 GPS 관측시각 저장이 활성화됩니다. 원본 시트와 월별 복사본이 모두 있는 경우 적용 직전에 차이를 대조해야 합니다. 구형 서버가 원본에 쓴 변경을 확인하기 전에는 원본을 삭제하거나 이름을 바꾸지 않습니다.
